# 이투데이 공급·구매 사건의 표본과 판정

2020년 1월 1일부터 2024년 12월 31일까지 이투데이 일별 사이트맵에서 제목에 삼성전자·하이닉스·네이버 또는 사전 지정한 영문·한자 표기가 들어간 고유 URL 8,842개를 모았다. 월별 XML의 추가 URL도 제목과 원 게시일을 대조했다. 회사명이 본문에만 나오는 보도는 이 표본에서 빠진다. 제목 검색에는 자회사나 유사 명칭도 포함될 수 있어 사건을 판정할 때 상장 본사의 역할을 다시 확인했다.

## 사건을 기록하는 기준

1. 원기사 본문 영역에서 계약, 수주, 발주, 공급사 선정, 위탁생산, 중계권 확보, 위탁 종료 등 표현을 검색한다. 원문이 없는 속보와 개발 기간 이후 수정판만 남은 기사는 결측으로 기록한다. 원문은 로컬에 보관한다.
2. 구매자나 공급자가 제품·서비스와 상대방을 특정하여 거래 체결이나 최종 선정을 발표했는지 본다. 공시, 확정된 공공조달, 대회 중계권 매입, 특정 고객의 신제품용 생산자 최종 채택을 포함한다. 금액 공개는 필수 조건이 아니다. 제품 시험, MOU, 수주 전망, 지분 취득, 단순 제휴, 제재에 따른 출하 중단, 기존 납품 실적 소개는 각각 구분한다. 자회사 단독 계약, 증권사 전망, 확인되지 않은 단독설도 제외 사유로 적는다. 해지에는 특정 공급·구매 계약에 대한 종료 결정 근거를 요구한다.
3. 발표를 다시 인용한 기사는 같은 사건과 보도 묶음 ID를 사용한다. 한 공시에서 두 발주처 또는 별도 사업장의 독립 계약 두 건을 확인하면 추가 사건 ID를 둔다. 같은 프로젝트에 관한 수주 전망·현장 개장·시황 해석은 새 수주로 더하지 않는다.
4. 신호에 사용할 수 있는 시각은 확인 가능한 최종 판본의 수정시각이며 수정 표시가 없으면 게시시각이다. 수정 전 문구를 복원할 수 없는 구간과 누락 기사는 일별 입력 생성 단계에 전달한다.

집계 단위는 개인이 모든 기사에 붙인 수작업 라벨과 다르다. `prior_review`는 앞선 제목 후보의 개별 검토, `body_adjudication`은 추가·재검토 판정표의 기사별 기록, `body_screen`은 검색 후보 중 별도 채택·경계 사례 메모 없이 제외한 행이다. `revised_article_without_cue`는 검색 표현이 없는 수정 기사로 의사결정 시점의 정보 공백 점검에 쓴다. 기업명 필터와 본문 표현 검색 모두 추가 누락을 만들 수 있다. 기사에서 관찰한 사건 횟수는 기업의 전체 거래 횟수를 측정하지 않는다.

- 네이버가 세종 데이터센터 설계팀을 최종 선정한 발표, 도쿄 올림픽 온라인 중계권을 확보한 발표는 각각 구매 사건이다. [세종 데이터센터](https://www.etoday.co.kr/news/view/1853817) · [올림픽 중계권](https://www.etoday.co.kr/news/view/2044949)
- 같은 공기질 데이터 제공 발표를 KT 쪽 기사는 공급계약, 네이버 쪽 기사는 업무협약으로 표현했다. 거래 역할을 특정한 KT 발표를 기준으로 한 번 집계했다. [KT 발표](https://www.etoday.co.kr/news/view/1962760) · [네이버 발표](https://www.etoday.co.kr/news/view/1962964)

## 재생성 및 판정 변경

프로젝트 루트에서 다음 순서로 실행한다. 사이트맵 캐시의 선행 수집 절차는 `src.news_archive`에 있다.

```text
python -m src.contract_review collect
python -m src.contract_review queue
python -m src.contract_review finish
python -m src.contract_review check-freeze
```

`contract_audit.json`에 본문 판본, 시점, 수작업 판정 파일별 내용, 기존 원장, 후보 추출식, 후보 키 목록, 최종 행과 결측의 해시를 기록한다. 일반 재생성은 어떤 해시든 변경되면 원장 파일을 쓰기 전에 멈춘다. `check-freeze`는 임시 사본에서 확인된 태양광 계약 판정 한 줄을 실제로 지우고 동일한 검사가 실패하는지 확인한다.

판정을 의도적으로 변경하는 경우 해당 기업·기사·사건 ID, 근거 및 이전 판정과의 차이를 판정 파일과 Git 변경 기록에 남긴다. 누락된 판정 파일을 먼저 확인하고, 후보 추출식을 변경했다면 추가·탈락 후보도 다시 검토한다. 동일한 원문 판본에 대한 의도된 수정은 `python -m src.contract_review finish --refresh-adjudication`으로 봉인된 판정과 집계를 갱신하고 일반 재생성 및 `check-freeze`로 확인한다. 이후 일별 신호도 다시 생성한다. 원문 판본 자체가 바뀐 경우에는 이전 버전을 보존하고 바뀐 기사와 시점을 검토하여 별도의 데이터 버전을 만든다.
